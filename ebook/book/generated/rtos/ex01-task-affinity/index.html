Goal: understand how to pin a task to a CPU core, how two cores run two tasks at once, and what affinity does not give you for free.

What this exercise is not: IPC between cores, spinlocks, or “make my app twice as fast.” Pinning is placement, not a speed cheat code.

2. Mental model — two cores, one firmware image

ESP32-S3 is a dual-core Xtensa chip. FreeRTOS (ESP-IDF SMP) runs a scheduler on each core. A pinned task may only be Running on its chosen core.

┌─────────────────────┐     ┌─────────────────────┐
│       core 0        │     │       core 1        │
│  scheduler + tasks  │     │  scheduler + tasks  │
│  (this lab: core0)  │     │  (this lab: core1)  │
└─────────────────────┘     └─────────────────────┘
            \                     /
             \   shared RAM      /
              \  heap / TCBs    /
               \_______________/

Analogy: two kitchens in one restaurant. Affinity says which kitchen a cook works in. The pantry (RAM) is still shared — so you still need discipline when two cooks touch the same shelf (later: mutex / queue).

Unpinned tasks: xTaskCreate (or pin with tskNO_AFFINITY) lets the scheduler migrate the task between cores. That is fine for many jobs; pin when you care about locality, ISR pairing, or isolating heavy work.

5. Scheduler picture (dual core)

On each core, the familiar state machine still holds:

  Running              Blocked               Ready             Running
┌──────────┐ vTaskDelay ┌──────────┐  tick  ┌──────────┐ pick ┌──────────┐
│  core0   │ ─────────► │  core0   │ ─────► │  core0   │ ───► │  core0   │
│  logs    │            │  waiting │        │ wants CPU│      │  logs    │
└──────────┘            └──────────┘        └──────────┘      └──────────┘

The new fact: core1 can be Running at the same wall-clock time as core0. That is true parallelism for two Ready tasks pinned apart — something a single core can only fake by switching.

ESP-IDF default: protocol / Wi-Fi often live on a specific core. Your app tasks share those cores with system work. Pinning everything to core 1 “to leave core 0 alone” is a strategy — measure before you believe it.

7. Tips and tricks (from the lab bench)

Tip — pin for a reason, not for decoration

Good reasons: keep a fast control loop away from Wi-Fi; run UI on one core and DSP on the other; match a peripheral ISR’s core. Bad reason: “dual core means I must pin everything.” Unpinned can be simpler and still correct.

Tip — shared data is still shared

Two cores writing the same global without sync is a data race — often worse than on one core because true overlap is more likely. Affinity is not a mutex. This lab avoids sharing mutable state on purpose.

Tip — LCD / drivers may live on one core

Logging from both cores into a display helper that takes a lock is OK if the lock is correct. If a driver is “core 0 only” by design, calling it from core 1 can deadlock or corrupt. Know your BSP. Our ex_terms_log path uses the display lock inside rb_term — fine for demos; still treat UI as a shared resource.

Tip — same stack / prio rules as ex00

Stack size is still in words. arg must still outlive the task. pdPASS still matters. Pinning does not fix a too-small stack.

Tip — tskNO_AFFINITY vs hard pin

ChoiceUse when
Pin 0 / 1You need a stable home core
tskNO_AFFINITYSoft real-time work that can migrate
Only xTaskCreateSame as no affinity on ESP-IDF

Tip — proving affinity in reviews

In code review we ask: “Where do you print / assert xPortGetCoreID()?” If the answer is nowhere, the pin is a hope, not a verified property.

Tip — load balance is not automatic magic

Pinning two light tasks to two cores looks great on this LCD. Pinning ten heavy tasks all to core 1 makes core 0 idle and core 1 late. Design the map; then measure (task monitor / runtime stats — later labs).

8. Focus / avoid / consider

Focus on

  • xTaskCreatePinnedToCore’s last argument
  • Reading xPortGetCoreID() every loop
  • “Two Running tasks at once” vs ex00’s time-slicing story

Avoid

  • Assuming pin doubles performance
  • Sharing writable globals across cores with no sync
  • Pinning every task “because the chip has two cores”
  • Forgetting system tasks already occupy both cores

Consider

  • What if both tasks pin to core 0? (Back to single-core contention.)
  • What if one task is unpinned? (May migrate; cN can change.)
  • Where should a future queue producer / consumer live?

11. Experiments

  1. Pin both tasks to core 0 — both panes show c0; they take turns.
  2. Pin both to core 1 — same story on the other CPU.
  3. Use tskNO_AFFINITY for one task — watch whether cN ever flips.
  4. Drop one task’s vTaskDelay — that core stays busy; the other core’s pane still advances (true parallel contrast to ex00 starvation demos).
